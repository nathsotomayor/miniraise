# MiniRaise — Spec

A tiny learning project: an investment checkout page built with Ruby on Rails and Svelte.
It is a personal demo inspired by online capital-raising platforms. It is not affiliated
with any company, and it handles no real money.

## 1. Why this exists

- Learn the basics of Svelte by building one real component inside a Rails app.
- Practice a full AI-assisted workflow: spec, plan, implementation, tests, review, delivery.
- Apply basic UX and frontend good practices through Claude Code skills and tooling,
  instead of relying on memory.
- Ship it the way a real team would: CI on every pull request, a production Docker
  image, and automatic publishing of that image on merge.
- Keep a short log of what worked and what did not at each step.

**Timebox: 4 hours for slices 1 to 4.** If slice 1 is not running after 2 hours, stop.
Slice 5 (Docker and delivery) has its own 45-minute timebox and can be done on another day.
If time runs short, drop slice 6 first, then slice 5, then visual polish. Never drop the
accessibility and state requirements in section 7, or the CI checks from slice 1.

## 2. What the user can do

1. Open the page of one offering (a company raising capital).
2. See the offering name, the target amount, how much has been raised, the number of
   investors, and a progress bar.
3. Fill a form (name, email, amount) and submit an investment.
4. See the progress bar and totals update immediately, without a page reload.
5. See a clear error message if the investment is invalid.

## 3. Out of scope

Product: authentication, payments, KYC, admin screens, multiple pages, UI component
libraries, CSS frameworks, animations beyond a simple progress transition, real-time
updates between browsers, internationalization.

Infrastructure: Docker Compose, Kamal, Kubernetes, dev containers, multi-architecture
images, staging environments, external databases, secrets managers, monitoring.
Local development stays native (`bin/dev`), not inside Docker.

Do not add anything that is not in this spec. If something seems missing, ask first.

## 4. Stack

- Ruby on Rails (latest stable), SQLite.
- `vite_rails` for the frontend build.
- Svelte 5 (runes: `$state`, `$derived`, `$props`) with `@sveltejs/vite-plugin-svelte`.
- One Svelte component mounted inside a normal Rails ERB view. No SPA router, no Inertia.
- Plain CSS with custom properties. No Tailwind, no component library.
- RSpec for request and model specs.
- RuboCop and Brakeman as generated by Rails.
- GitHub Actions for CI and delivery. Docker for the production image.
  GitHub Container Registry (`ghcr.io`) to store the image.

When generating the app, skip what this project does not use (the default test
framework, mailers and mailboxes, Action Text, Active Storage, Action Cable, Hotwire,
Jbuilder, Kamal, and the Solid adapters), and keep the generated Dockerfile, CI
workflow, RuboCop, and Brakeman. Check `rails new --help` for the exact flags and list
them in the slice 1 plan.

## 5. Data model

**Offering**
- `name` (string, required)
- `target_amount_cents` (integer, required, > 0)
- `min_investment_cents` (integer, required, > 0)

**Investment**
- `offering_id` (reference, required)
- `investor_name` (string, required)
- `investor_email` (string, required, valid email format)
- `amount_cents` (integer, required, >= offering's `min_investment_cents`)

`investor_email` is stripped and downcased before validation.
`investor_count` in the API is the number of distinct investor emails for the offering,
not the number of investments. `raised_amount_cents` is the sum of all investments.

Money is always stored as integer cents. Seed one offering with a fictional name and
three or four investments. Seeds must be safe to run more than once.

## 6. API

**GET `/api/offerings/:id`**

```json
{
  "id": 1,
  "name": "Solar Kettle Co.",
  "target_amount_cents": 50000000,
  "min_investment_cents": 10000,
  "raised_amount_cents": 12500000,
  "investor_count": 4
}
```

**POST `/api/offerings/:id/investments`**

Request body:

```json
{ "investment": { "investor_name": "Ana", "investor_email": "ana@example.com", "amount_cents": 25000 } }
```

- `201` with the same JSON shape as the GET endpoint (updated totals).
- `422` with `{ "errors": { "amount_cents": ["must be at least 100.00"] } }`.
- `404` if the offering does not exist.

## 7. UI and UX requirements

### Behavior

- Rails route `GET /offerings/:id` renders an ERB view.
- The view renders a mount point and passes the offering id to the Svelte component.
- Component `InvestmentCheckout.svelte`:
  - Loads the offering from the GET endpoint when it mounts.
  - Shows name, raised amount, target amount, investor count, and a progress bar.
    The percentage is a derived value, not stored state.
  - Form with name, email, and amount in dollars. Convert to cents before sending.
  - On `201`, replaces local state with the response and clears the form.
  - On `422`, shows each error next to its field.
  - Sends the Rails CSRF token in the request header.

### States (every one must be designed, not left to chance)

| State | What the user sees |
| :- | :- |
| Loading | A placeholder with the same dimensions as the loaded content, so nothing jumps |
| Loaded | Offering data, progress bar, form |
| Load failed | A short message and a "Try again" button |
| Submitting | Submit button disabled, label changes to "Investing…" |
| Submit succeeded | A confirmation message, updated totals, cleared form |
| Validation error | Error text next to each invalid field, values preserved |
| Network error on submit | A message above the form, values preserved |

### Forms

- Every input has a visible `<label>` linked with `for` and `id`. No placeholder-only labels.
- Use the right input attributes: `type="email"`, `inputmode="decimal"` for the amount,
  `autocomplete="name"` and `autocomplete="email"`, `required` where it applies.
- Show the minimum investment as helper text under the amount field before any error.
- Validate on submit, then re-validate a field as the user corrects it. Do not show
  errors while the user is still typing for the first time.
- Error messages say what to do, in plain language: "Enter at least $100.00".
- Never clear what the user typed when a request fails.

### Accessibility

- Semantic HTML first: one `<h1>`, `<main>`, `<form>`, `<button type="submit">`.
- Progress bar is a native `<progress>` or has `role="progressbar"` with
  `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, and a text alternative.
- Errors are linked to their field with `aria-describedby`, and invalid fields set
  `aria-invalid="true"`.
- Success and error messages are announced through an `aria-live` region.
- After a failed submit, focus moves to the first invalid field.
- Everything works with the keyboard alone, and focus is always visible.
- Text and controls meet WCAG AA contrast (4.5:1 for body text).
- Fix every accessibility warning from the Svelte compiler. Do not silence them.

### Layout and visual basics

- Mobile first: design for 360px wide, then widen. Single column, max content width
  around 480px, centered on larger screens.
- Touch targets at least 44px tall.
- Define colors, spacing, radius, and font sizes once as CSS custom properties in
  `:root`, and use only those values in components.
- Format money with `Intl.NumberFormat` (currency, USD). Never concatenate "$".
- Respect `prefers-reduced-motion` for the progress bar transition.

## 9. CI, Docker, and delivery

Principle: start from what Rails generates and change only what this project needs.
One workflow file, one Dockerfile, no extra services.

### 9.1 Continuous integration (slice 1)

One workflow, `.github/workflows/ci.yml`, adapted from the Rails-generated file.
It runs on every pull request and on every push to `main`.

| Job | What it does |
| :- | :- |
| Security scan | Brakeman, as generated |
| Lint | RuboCop, as generated |
| Test | Install Ruby gems and Node packages (both cached), build the frontend with Vite, prepare the test database, run RSpec |

Rules:

- Remove generated jobs and steps this project does not use (for example system tests
  or a JavaScript dependency audit for a tool that is not installed).
- The Vite build must run in CI, so a Svelte compile error fails the pull request.
- Use the dependency caching built into the official Ruby and Node setup actions.
  No hand-written cache steps.
- Keep the action versions that Rails generated. For any action you add, use its
  current major version.
- Target: the whole workflow finishes in under 5 minutes.
- A pull request is merged only when every job is green.

### 9.2 Production image (slice 5)

Adapt the Rails-generated `Dockerfile`, `.dockerignore`, and `bin/docker-entrypoint`.
Do not rewrite them.

Requirements:

- Multi-stage build. Node and `node_modules` exist only in the build stage, to compile
  the frontend. The final image contains no Node, no `node_modules`, no specs, and no
  development or test gems.
- Order the build so dependency layers are cached: copy the gem and package manifests
  and install dependencies before copying the application code.
- The final image runs as a non-root user and listens on port 80, as generated.
- `.dockerignore` excludes `.git`, `node_modules`, `log`, `tmp`, `storage`, `spec`,
  and local environment files.
- The entrypoint prepares the database on boot, so a fresh container creates and
  seeds it without manual steps.
- SQLite lives in `/rails/storage`, mounted as a named volume so data survives restarts.
- The only required environment variable is `SECRET_KEY_BASE`. Do not bake any secret
  into the image, and do not require the Rails master key.
- The container must work over plain HTTP on localhost. Put the production SSL
  enforcement settings behind an environment variable that is on by default, and
  document how to turn it off for a local run.

Acceptance check, documented in `README.md` with the exact commands:

1. `docker build -t miniraise .` succeeds.
2. Running the image with a port mapping to 3000, a generated `SECRET_KEY_BASE`, the
   SSL variable turned off, and a named volume starts the app.
3. `http://localhost:3000/up` returns 200.
4. `http://localhost:3000/offerings/1` shows the page, and an investment can be submitted.
5. After stopping and starting the container again, the investment is still there.

### 9.3 Delivery (slice 5)

Add one job, `image`, to the same `ci.yml`. It depends on the three jobs in 9.1.

- On pull requests: build the image, start a container from it, and check that `/up`
  returns 200. Do not push anything.
- On pushes to `main`: do the same, then push the image to
  `ghcr.io/<owner>/<repository>` with two tags: `latest` and the commit SHA.
- Authenticate to the registry with the workflow's built-in `GITHUB_TOKEN`. Grant the
  job only `contents: read` and `packages: write`. No personal tokens, no repository
  secrets.
- Use the official Docker build action with the GitHub Actions layer cache.

Deploying the published image to a hosting platform is slice 6 and is optional.

## 10. Slices (one branch and one pull request each)

1. **Scaffold and CI.** New Rails app, `vite_rails`, Svelte plugin, and a "hello" Svelte
   component rendering inside an ERB view. Create `CLAUDE.md`, the `frontend-ux` skill,
   and the `:root` CSS custom properties. Adapt the generated CI workflow per 9.1 and
   see it green on this pull request. This is the riskiest step, so it goes first.
2. **Backend read path.** Models, validations, seeds, GET endpoint, model and request specs.
3. **Frontend read path.** `InvestmentCheckout.svelte` loads and displays the offering
   with the progress bar. Covers the loading, loaded, and load failed states.
4. **Write path.** POST endpoint with specs, form, error handling, live update. Covers
   the submitting, success, validation error, and network error states.
5. **Docker and delivery.** Production image per 9.2 and the `image` job per 9.3.
   Own 45-minute timebox.
6. **Stretch: deploy.** Run the published image on a simple hosting platform.

## 11. Working rules for the AI agent

- Before each slice, propose a short plan and wait for approval. Do not write code first.
- Work on one slice at a time. Keep each pull request small and easy to review.
- Write or update specs in the same slice as the code they cover.
- For slices 3 and 4, the plan must include the list of UI states and a short
  description of the layout before any code.
- For slices 1 and 5, the plan must list which generated files change and why, line
  by line for the workflow and the Dockerfile. Prefer deleting to adding.
- Before each merge, run `/code-review`, then list risks, missing tests, and anything
  that differs from this spec. Do not merge with a red CI job.
- If CI fails, read the job log, explain the cause in one or two sentences, and then
  fix it. Do not retry blindly and do not disable a check to get to green.
- After writing or changing any Svelte file, explain it in plain language: what each
  rune does, how data flows, and how it compares to doing the same with ERB and
  vanilla JavaScript. The author is new to Svelte and must be able to explain every line.
- After changing the workflow or the Dockerfile, explain each change in one line.
- Do not add dependencies beyond the stack above without asking.
- After each slice, append an entry to `NOTES.md` (see below).
